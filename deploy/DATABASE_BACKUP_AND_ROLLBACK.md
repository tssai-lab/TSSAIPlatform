# PostgreSQL 备份与部署回滚规划

## 1. 文档状态

- 当前状态：规划完成，暂缓开发。
- 当前决定：该能力不阻塞后端自动化部署，后续作为数据库容灾能力单独建设。
- 适用环境：Main 服务器 PostgreSQL，以及后续新增的后端运行节点。

## 2. 背景

当前 `backend-ops` 分支已经实现以下自动化流程：

1. 推送后端代码。
2. GitHub Actions 自动运行测试。
3. 自动构建并发布不可变 Docker 镜像。
4. 自动将镜像部署到 Main。
5. 自动执行后端健康检查。
6. 新版本启动失败时，自动恢复上一个后端镜像。

现有回滚只处理后端程序，不处理 PostgreSQL。后端使用 Flyway 管理数据库结构，新版本启动时可能自动执行 `backend/src/main/resources/db/migration` 下的迁移脚本。

## 3. 核心原则

### 3.1 程序回滚和数据库恢复必须分开

- 程序回滚：可以自动执行。
- 数据库备份：可以自动生成。
- 数据库整体恢复：不得因程序部署失败而自动执行，必须经过人工确认。

原因是数据库备份完成后，系统仍可能产生新的正常业务数据。如果程序部署失败后自动恢复旧备份，这部分正常数据也会被删除。

### 3.2 数据库备份是保险，不是每次代码回滚的附属动作

备份主要用于以下严重情况：

- 数据库文件损坏。
- 业务表或业务数据被误删。
- Flyway 迁移严重错误且无法向前修复。
- 数据转换逻辑批量写入错误数据。
- 服务器磁盘故障导致数据库不可用。

普通后端启动失败、接口异常或镜像错误，优先只回滚后端程序，不恢复数据库。

### 3.3 数据持久化、主从复制和数据库备份不是同一件事

- 持久化存储防止容器删除时数据丢失。
- 主从复制降低单台服务器故障带来的影响。
- 数据库备份用于恢复历史状态和处理误操作。

错误 SQL 也可能同步到副本，因此主从复制不能代替备份。

## 4. 计划中的处理流程

### 4.1 普通代码部署

```text
推送代码
  -> 测试并构建镜像
  -> 部署新后端
  -> 健康检查
  -> 成功后结束
```

### 4.2 新后端部署失败

```text
新后端健康检查失败
  -> 自动恢复上一个后端镜像
  -> 数据库保持不动
  -> 检查旧后端健康状态
```

### 4.3 数据库出现严重问题

```text
发现数据库异常
  -> 暂停业务写入或进入维护状态
  -> 保留当前数据库现场
  -> 分析迁移记录和受影响数据
  -> 优先使用修复 SQL 或修复版本向前处理
  -> 无法修复时由管理员选择恢复点
  -> 执行数据库恢复
  -> 校验表结构、数据量和核心业务接口
```

## 5. 后续开发方案

### 5.1 第一阶段：基础备份

- 为 Main PostgreSQL 增加定时 `pg_dump` 备份。
- 备份保存到独立目录，不能只保存在数据库容器内部。
- 为备份文件记录时间、数据库名称、文件大小和校验值。
- 设置保留数量或保留天数，防止备份占满磁盘。
- 备份失败时发送告警，但不直接停止普通无数据库迁移的代码部署。

### 5.2 第二阶段：迁移感知

- 检测本次提交是否修改 Flyway 迁移文件。
- 检测到数据库迁移时，在部署前额外生成一次备份或恢复点。
- 迁移前备份失败时，阻止本次涉及数据库变化的部署。
- 记录部署提交号、镜像号、Flyway 版本和备份文件之间的对应关系。

### 5.3 第三阶段：恢复能力

- 编写需要人工确认才能执行的恢复脚本。
- 恢复前自动保存当前数据库现场，避免二次误操作。
- 支持恢复到指定备份，而不是默认恢复最新备份。
- 定期在隔离环境进行恢复演练。
- 正式生产阶段评估 PostgreSQL WAL 归档和时间点恢复（PITR）。

## 6. 数据库迁移约束

为了保证程序可以安全回滚，Flyway 迁移应尽量保持向后兼容：

- 优先新增字段，不立即删除或重命名旧字段。
- 新旧后端需要在过渡期同时兼容数据库结构。
- 数据迁移与旧字段删除分成不同版本完成。
- 删除表、删除字段、大批量数据转换必须单独评审。
- 优先通过新迁移向前修复，不把数据库降级作为常规方案。

## 7. 验收标准

后续实现完成后，至少满足以下条件：

1. 可以自动生成有效的 PostgreSQL 备份。
2. 备份文件不依赖后端容器生命周期。
3. 可以校验备份文件是否完整。
4. 可以在隔离环境成功恢复备份。
5. 程序部署失败时只回滚程序，不自动恢复数据库。
6. 数据库恢复操作需要明确的人工确认。
7. 恢复后可以验证 Flyway 版本、核心表和核心业务接口。
8. 备份文件有清理策略，不会持续占满服务器磁盘。

## 8. 与当前自动化部署的关系

当前后端自动化部署可以继续使用，不等待本文档中的数据库备份能力完成。

现阶段应保持以下边界：

- GitHub Actions 继续自动测试、构建和部署 `backend-ops`。
- Main 继续自动进行后端健康检查和程序镜像回滚。
- 不增加数据库自动整体恢复动作。
- 在数据库备份能力开发完成前，涉及破坏性 Flyway 迁移的提交必须人工评审。
