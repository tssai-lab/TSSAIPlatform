# 推理失败任务手动重试

## 对外行为

- 登录用户通过 `POST /api/inference/tasks/{taskId}/retry` 重试自己拥有的失败任务；管理员沿用推理任务现有的跨用户访问规则。
- 只有 `failed` 状态可以重试。任务 ID 保持不变，每次成功受理会增加 `currentAttempt` 和 `retryCount`，默认最多重试 3 次。
- 重试受理前会重新校验模型、脚本和输入数据的可用状态及当前用户访问权限。校验失败不会消耗重试次数。
- 重试会清空上一尝试在任务主记录中的结果、日志、输出、错误、时间和执行节点信息；各次对象存储输出仍按 `attempt-N` 隔离，删除任务时一并清理。
- 列表、详情及结果响应返回 `currentAttempt`、`retryCount`、`maxRetries`、`retryable` 和 `lastRetryAt`。
- 接口继续使用现有 Legacy `ApiResponse` 返回格式。

## 并发和失败恢复

- 重试事务使用任务行锁。同一失败状态的并发请求只有一个可以增加尝试次数，后到请求会看到已变更状态并被拒绝。
- 事务提交后，调度器通过原子状态更新抢占提交权，避免重复提交同一尝试。
- 尚未提交或提交中断的 `pending`、`queued`、`scheduled` 任务会被定时恢复；恢复使用原尝试编号，不额外消耗重试次数。
- Worker 回调必须携带 manifest 注入的 `attempt`。重试后缺少 `attempt` 的旧版回调会被忽略；尝试编号不匹配、终态后的重复回调以及状态或进度倒退也会被忽略。

## 当前业务假设

以下规则来自现有待完成功能和项目习惯，当前没有独立需求文档：

- 最大重试次数为 3 次。
- 所有失败原因都消耗一次重试次数，不区分用户输入错误和基础设施错误。
- `stopped` 任务不能重试。
- 任务主记录只展示当前尝试；旧尝试的对象存储目录保留到删除任务时清理，未新增尝试历史表。

如果这些业务规则要改变，需要同步确认对外 API、用户界面和数据保存策略。
