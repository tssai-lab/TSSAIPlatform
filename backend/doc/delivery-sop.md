# 单机交付收口 SOP

目标：甲方在一台 NVIDIA GPU 服务器上自行安装平台，后续可接入更多计算节点。

## 执行规则

1. 先代码、再部署、最后手册；各阶段独立提交和验证。
2. 以当前内网已发布代码为基线，保留外网 CPU 环境隔离；不得静默向外网发布。
3. 删除必须有引用依据；保留已执行数据库迁移、正常测试、实际依赖的旧 API 和 kubectl。
4. 不改变用户资产、权限模型或数据库结构；失败、重复请求、清理与资源隔离是回归重点。
5. 中文注释重点解释职责、事务、幂等与失败行为；不批量翻译生成文件、第三方代码和已执行 SQL。

### 安装阶段继续遵循的规则

1. 保留当前 kubeadm/containerd 与 Docker Compose 的分工。客户配置替代实验室身份、节点数、Git checkout、双盘 UUID 等假设；不得直接放宽 `tss-aiplatform-internal` 安装脚本的保护条件。
2. 单机默认只在明确选定的控制节点开放计算，并配置 kubelet 的系统/Kubernetes 资源预留。当前五个 Compose 服务的内存上限合计 5.25 GiB、CPU 上限合计 3.75 核；这还不含操作系统、控制面、网络及监控，不能把全部物理资源开放给训练。预留值需结合实际机器确认，不以当前空闲量充当硬容量。
3. 平台镜像导入 Docker；训练、推理、前端及 Kubernetes 组件导入项目 containerd 的 `k8s.io` 命名空间。一个运行时导入成功不等于另一个运行时可用；同一归档可分发，不重复打包同一镜像内容。
4. 镜像按已部署版本的锁文件和摘要整理。项目包默认为 11 个（前后端 2、CPU/GPU 训练 4、CPU 推理 1、MLflow-lite 1、PostgreSQL/Redis/MinIO 3）；13 个 Kubernetes 基础组件镜像在安装时联网获取，不默认归档。网络、DNS、Metrics、NVIDIA、DCGM 和 RuntimeClass 的配置与验证仍需纳入手册；联网不等于可随意升级或从不明源下载。
5. 使用新数据库与新生成凭据，通过 Flyway 初始化；不复制实验室账号、旧用户数据或管理员 kubeconfig。后端继续使用项目 ServiceAccount 的最小权限。
6. 新增计算节点先完成对应系统依赖、镜像、GPU 驱动、网络、监控和缓存目录；加入后经真实资源检测再开放调度。数据库与权威资产仍在原节点，扩容不等于存储高可用。
7. 安装可重复执行与恢复是验收项：已有不明数据不覆盖，失败停在可诊断步骤，不全量 reset；需复演“基础环境联网安装—项目镜像导入—功能验收—重启恢复”，不再要求整套环境断网安装。没有可用于平台新装的测试机器时，只能提交脚本/配置测试结果，不能宣称完成实装。
