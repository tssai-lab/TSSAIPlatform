# 后端架构与功能扩展指南

核对日期：2026-09-10；生产代码基线 `30dda00`。下文 B 路径相对本仓库；J 表示 `backend/src/main/java/com/tss/platform/`；T 表示 `backend/src/test/java/com/tss/platform/`。本文件可独立随后端源码交付。

## 1. 后端分成哪几层

Java 17 / Spring Boot 后端在 `backend/` 中，是一个应用工程。业务接口处理、后台调度与状态管理在 Java 中；实际训练/推理还会运行 `k8s/` 中的 Python worker。

| 位置 | 大白话职责 | 新功能落点 |
| --- | --- | --- |
| J：`TssPlatformApplication.java` | 启动应用并开启定时调度 | 框架启动级配置 |
| J：`controller/`、`controller/v2/` | 接收请求，调用业务，返回结果 | 新接口放相邻业务控制器；V2 包名不自动等于 URL 前缀 |
| J：`dto/` | 请求和响应的字段格式 | 新参数、返回字段和参数校验 |
| J：`service/` | 处理业务规则、事务、存储调用和恢复 | 新功能的主要业务逻辑 |
| J：`entity/`、`repository/` | 数据库记录及 JPA 查询 | 资产、版本、任务等持久化 |
| J：`model/`、`asset/spec/` | 状态/值对象/Manifest 数据结构，以及资产格式规范 | 新状态、新资产格式及消费证据 |
| J：`module1/` | 正式账号、角色、用户 API 策略、日志和审计 | 这里沿用 Controller/Service/MyBatis Mapper 分层 |
| J：`config/`、`security/` | 运行配置、登录上下文、过滤器和基础设施 | 全局认证、存储、执行参数等 |
| J：`training/`、`training/plan/` | 训练方案、运行快照、执行器、Kubernetes 作业和监控 | 新训练能力、资源和运行协议 |
| J：`inference/` | 推理调度、资源规格和 Kubernetes 执行 | 新推理运行能力 |
| J：`modelcache/` | 模型缓存策略值对象和卷命名 | 与缓存 Service 配合修改 |
| B：`backend/src/main/resources/` | 应用配置、SQL、训练方案和模板 | 配置项、数据库迁移、内置方案 |
| B：`backend/src/test/`、`backend/scripts/qa/` | 单元、API、数据库/存储测试及报告门 | 为变化补边界和真实依赖验证 |
| B：`k8s/`、`deploy/`、`examples/`、`.github/workflows/` | 运行程序、部署交付、示例和自动化 | 业务需要新增运行环境或交付能力时 |

普通资产/任务链路是 Controller → Service → Repository → PostgreSQL。用户/日志链路主要是 `module1/controller` → `module1/service` → `module1/mapper` → PostgreSQL。两种访问方式在同一个应用中并存；新需求沿用所属模块的方式，不顺带切换持久化框架。

## 3. 数据存在哪里，字段应该加在哪里

| 数据 | 存储及代码入口 | 扩展注意点 |
| --- | --- | --- |
| 模型/数据集/代码资产与版本、实验、推理任务、配置 | PostgreSQL；J 的 `entity/`、`repository/` | 先分清资产、版本、上传会话和任务；不能只按页面表单建字段 |
| 用户、角色、操作日志、接口策略 | PostgreSQL；J 的 `module1/entity/`、`module1/mapper/`；B 的 `backend/src/main/resources/mapper/` | 部分查询为 Mapper XML，部分由 MyBatis Plus/注解完成 |
| 权重、数据文件、代码 ZIP、训练/推理结果 | MinIO；`service/MinioService.java` 和业务存储封装 | 数据库只保存引用/状态等记录；校验归属、路径、清理与失败补偿 |
| 登录状态及用户 API 并发控制 | Redis；认证配置、`module1/security/` | 新策略要考虑退出/失效、并发请求结束后的额度释放 |
| 训练实验指标 | MLflow；Java 跟踪服务、训练 worker、前端 MLflow 代理 | 保留 run/experiment 关联；0、没有数据和请求失败分别处理 |
| LeRobot Parquet 内容查询 | DuckDB 预览逻辑 | 属于预览读取工具；业务状态仍由 PostgreSQL 管理 |

数据库迁移在 B：`backend/src/main/resources/db/migration/`。用户基础建表另有 `backend/src/main/resources/db/module1-schema-postgresql.sql`，审计初始化还有 `config/AuditSchemaInitializer.java` 与审计 SQL。新增字段应同时检查已有迁移、模块初始化和历史数据升级路径。

2026-09-10 该目录实际已有 V65，目录 README 的“最高 V60”尚未跟上。新编号要按目标分支已有脚本及待合并迁移重新确认，不能仅凭旧说明取号；已执行的历史 SQL 保留原内容，结构演进使用新增迁移。

## 4. 训练和推理为什么可能要多处联动

训练主要链路：请求 DTO → `service/TrainingExperimentService.java` → `training/plan/TrainingRunSpecFactory.java` 固化输入和方案 → 调度/执行器 → Python → 内部回调 → 状态、指标、产出模型。保存运行快照是为了以后仍能解释旧任务用了什么配置。

- 方案定义和校验：J 的 `training/plan/TrainingPlanDefinition.java`、`TrainingPlanValidator.java`、`TrainingPlanRegistry.java`；B 的 `backend/src/main/resources/training-plans/`、`training-plan-templates/` 及 schema。
- 在线方案：管理员接口为 `/api/admin/training-plans`；`TrainingPlanAdministrationService` 管理数据库版本并更新方案注册表。在线方案不能覆盖同 ID/版本的内置方案。
- 训练执行：J 的 `training/TrainingExecutorRouter.java`。旧无 profile 任务走本地执行器；profile 任务要求 Kubernetes 就绪。作业构造/监控见同目录的 ManifestBuilder、Executor、JobMonitor。
- 训练 worker：B 的 `k8s/training-worker/train.py`，准备代码/模型/数据、参数、运行用户程序、整理输出和指标并回报后端；同目录 Dockerfile 和 requirements 决定运行依赖。
- 推理执行：J 的 `inference/InferenceExecutorRouter.java` 和 Kubernetes 执行类；B 的 `k8s/inference-worker/infer_worker.py` 运行用户脚本、上传结果和回调。任务重试使用 attempt 区分每次尝试。
- 内部回调：J 的 `controller/InternalTrainingCallbackController.java`、`InternalInferenceCallbackController.java` 及 `config/` 中的内部认证过滤器。新增结果字段要兼顾重复/迟到回调与已有任务状态。

新增算法先判断是否可由“训练方案 + 上传代码 + 已支持的镜像/输入输出格式”完成。超出当前能力才修改平台运行协议和 worker。训练示例见 B 的 `examples/training/`、`examples/acceptance/`，推理示例见 `examples/inference/`。

## 5. 新业务必须接上的公共边界

- **身份和功能范围：** J 的 `config/WebConfig.java` 注册 `module1/interceptor/PermissionInterceptor.java`；`module1/security/UserApiFeatureClassifier.java` 把 URL 分到六类用户 API 开关和限额。新增前缀需要检查分类，原例外不能直接照抄。
- **管理员、所有权与审计：** API 总开关不代替各业务的 owner、管理员、版本可消费和审批检查。代码管理员接口还有独立配置入口。
- **并发与事务：** 保留原本“先占位/校验、事务提交、远程操作、条件回写、失败补偿”的实际边界；具体顺序以所属业务原代码为准。CAS 是“只有状态仍符合条件才更新”，用于挡住重复和过期操作。
- **后台恢复：** 新的处理中状态需要考虑 JobScheduler、导入/上传恢复、模型发布和对象清理调度器。请求超时不能直接判为写入失败，也不能盲目重放。
- **接口兼容：** 现有业务响应及旧接口仍有差异；DTO、错误码、资产/版本编号变化，要同步前端适配和旧数据测试。根 `dto/ApiResponse.java` 不是全仓所有接口都使用的唯一响应形状。

先跑变化涉及的测试，再按[代码维护索引](代码维护索引.md)跑完整保护门。Maven 工程位于 B 的 `backend/`。本地隔离入口 `backend/scripts/qa/run-container-integration.sh` 支持 `--preflight` 和 `--all`；环境、镜像、缓存与证据目录要求见维护索引。真实集群测试需要独立配置及环境证据，单元测试或容器依赖测试不能代替实际作业。

运行与交付目录：`k8s/base/` 是基础 Kubernetes 配置，`k8s/kind/`、`k8s/local/` 为本地验证辅助；`deploy/customer/` 为客户交付准备，`deploy/tss-aiplatform-internal/` 为平台配置、脚本、清单和可重现交付资料，`deploy/scripts/` 为操作脚本。实际发版前核对 `deploy/README.md`、镜像锁及 workflow 的分支/目标环境。

新依赖、镜像或配置变更需同步交付材料，并验证新装/升级/重启；普通字段或页面变化通常无需改集群脚本。`backend/target/` 和测试缓存是生成物，真实数据和共享服务器文件均不作为代码修改目标。
